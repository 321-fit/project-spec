Welcome / Role pick

Entry screen for first-time install. Two ways forward: I'm a Coach (primary gradient) or I'm an Athlete (secondary outlined). Role is captured client-side and threaded through to sign-up / sign-in so server knows which onboarding to assign.

iOS ref: Authentication/Role/ChooseRoleView.swift (background image + welcome icon + 2 stacked buttons).

  • No back/close — this is the root of the unauthenticated stack.
  • Buttons use canonical .fit-btn-primary / .fit-btn-secondary with 50pt height + 99pt radius.
  • Returning users skip this entirely — auth state restores from keychain → goes straight to last role.

Background image (welcome-background asset on iOS) intentionally simplified here — prototype focuses on layout + interaction. Real asset lives in Resources/Images.xcassets/Authentification/welcomeBackground.

Sign-up · method picker

3 sign-up methods stacked: Email (primary), Apple (black pill), Google (secondary). Email first as the explicit / least-friction path; Apple second for iOS-first audience, Google third. Apple stays on iOS only (hidden on Android in production).

iOS ref: Authentication/SignUp/SignUpView.swift + AuthenticationAvailableTypes enum.

  • Canonical .fit-btn-primary / .fit-btn-secondary + page-local .fit-btn--dark-pill for Apple. Provider modifier .fit-btn--auth-provider only adds icon spacing.
  • Apple / Google open native OS sign-in sheets — no in-app screen for those flows.
  • "Sign in" at footer toggles into sign-in entry (next batch).
  • Layout matches account-access.html canon: pf-head (icon + title + sub) → au-btn-stack with 16px horizontal padding → footer toggle.

Phone is NOT a sign-up method as of 2026-05-11 per authentication.md. Phone is an outreach attribute, captured separately during signup for ownership verification (next batch).

Sign-up · email form

Email + password form. Validates client-side via inline password-rules list (mirrors account-access.html add-email-password pattern), posts to backend, advances to phone OTP step (next batch).

iOS ref: Authentication/SignUpWithCredentials/SignUpWithCredentialsView.swift (states: emailEntry → phoneEntry → codeEntry).

Field validation

  • Email — keyboardType: emailAddress, lowercase, RFC-5322 lite regex. Submit-on-Next moves to password.
  • Password — secure entry. Rule list below the field flips .pending → .ok as the user types (matches account-access add-email-password rule pattern). ≥8 chars + mix letters/digits + not a common dictionary password (server is source of truth per account-access.md).
  • Sign up button — disabled (0.5 opacity, no tap) until all 3 rules ok.

Server errors — 409 email-taken → pf-err-msg below email field "This email is already in use by another account."; 400 bad password → "Password too weak — 8+ chars, mix letters and digits."

Keyboard flow per feedback_keyboard_behavior: Email field Next → Password field Go → fires Sign up.
