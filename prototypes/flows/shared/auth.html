Sign up

Layout adopted 2026-08-20, after four candidates stood side by side on the board (wide buttons / circles / centred / generous rhythm). The winner is the last: top-anchored with the air doubled, providers as circles. Centring was tried and dropped — flip Keyboard open and note that nothing moves; a centred block had to jump ~240px the moment the keyboard arrived, and it put the CTA at a different height on every screen. The other three variants have been deleted rather than parked, so this file has one answer per screen.

One screen, not two (2026-08-20). The method picker that stood between the role choice and this form is gone: it asked you to choose a door before showing you any, and its email button led straight here. Role pick now lands on this screen. Email and password are the screen; the providers sit under an or continue with rule; the switch to the other mode is the footer.

Email + password with inline password-rules list. Posts to backend → advances to phone OTP step (next batch).

No password-rules list on arrival (2026-08-20). Three grey circles above the CTA, at the moment nothing has been typed, crowd the one thing the screen is for. The list now appears when a rule actually passes or fails — flip the Weak password / All rules ok states to see it. It stays permanently visible on the reset screen, where the whole screen is the password and nothing competes with it.

No "repeat password" — a second field to catch a typo the eye toggle already catches, on a password you can reset by email. The live Android build still has one; that is drift, not the design.

iOS ref: Authentication/SignUpWithCredentials/SignUpWithCredentialsView.swift (states: emailEntry → phoneEntry → codeEntry).

Components

  • Inputs: canonical fit-input-group + fit-input, no fit-input-label. Two fields whose names are one word each — a label above a placeholder that says the same thing is the label twice. The rule: the label or the placeholder names the field, never both. Keep the label where the placeholder is a format hint instead of a name (phone, the recovery screens).
  • Providers: circles — kit fit-icon-btn + page-local au-provider-circle (32 → 60px; 32 is a header affordance, a provider choice is a primary target). Under a page-local au-or rule, which names them, so the per-button label was saying it twice. They open native OS sheets — no in-app screen.
  • Rhythm: page-local au-air on fit-phone-content — heading 30px starting 44px down, fields 60px with a tight 13px gap between them, doubled seams between groups. Both auth screens share it, so the CTA lands in the same place on each.
  • Rule list: page-local au-pw-rules + au-pw-rule (with .ok / .fail states). Flips circle → check SVG as conditions met.
  • CTA: canonical fit-btn fit-btn-primary in au-cta-wrap (16px screen padding).

Field validation

  • Email — keyboardType: emailAddress, lowercase, RFC-5322 lite regex. Submit-on-Next moves to password.
  • Password — secure entry. ≥8 chars + mix letters/digits + not a common dictionary password (server source of truth per account-access.md).
  • Sign up button — disabled (0.5 opacity, no tap) until all 3 rules ok.

Server errors — 409 email-taken → fit-input-group.error on email + fit-input-error-text "This email is already in use."; 400 bad password → similar pattern on password field.

Keyboard flow per feedback_keyboard_behavior: Email Next → Password Go → Sign up.

Sign in

Same adopted layout as sign-up — au-air + circles, chosen from four variants on the board. Last used on this device is the teal ring around the provider circle: the ring marks the thing itself, where a dot beside it was a second object to decode. The aria-label carries it in words too.

Merged the same way as sign-up (2026-08-20) — the sign-in method picker is gone. Last used on this device survived the merge and moved onto the provider it describes: on the merged screen email is always in front, so the marker only earns its place beside a provider.

Email + password. Posts to backend → on success, lands on main app. On 401 → inline error banner above CTA. "Forgot password?" sits directly under the password field, right-aligned — it is about that field, and putting it below the CTA had made it look like an afterthought to signing in.

iOS ref: Authentication/SignInWithCredentials/SignInWithCredentialsView.swift.

  • Inputs: canonical fit-input-group + fit-input + fit-input-password + fit-eye-toggle.
  • No password-rules list here (unlike sign-up) — just sign in with whatever was set.
  • Forgot password link uses page-local au-forgot-link styled as secondary text under CTA (NOT inline next to label, per HIG — keeps the field clean).
  • Server errors:
    • 401 wrong credentials → generic banner "Email or password isn't right" (avoid disclosing which is wrong — security best practice).
    • 423 locked (too many failures) → banner with retry-after time + suggestion to use Forgot password.
    • 409 method-not-set (user signed up via Apple/Google, no email password) → banner "This email is signed in with Apple/Google. Tap to continue with that method instead."

Keyboard flow: Email Next → Password Go → fires Sign in. Same as sign-up.

Forgot password · step 1 — enter email

First step of password recovery. Single email field + Send code CTA.

iOS ref: Authentication/ForgotPassword/ForgotPasswordView.swift (type=email, contactField=emailTextfield).

  • Backend always responds 200 regardless of whether the email exists — prevents email enumeration. If email isn't on file, no code is actually sent; user lands on OTP step with no way to advance. Acceptable UX trade for security.
  • Validation: client-side email regex (same as sign-up); server doesn't validate format, just enqueues OTP if account found.
  • Rate limit: 1 request per email per 60 sec, 5 per hour. Server returns 429 on excess → banner "Slow down — try again in N seconds."

Forgot password · step 2 — OTP code

6-digit code entry. Page-local au-otp-boxes + au-otp-box (same pattern as account-access.html's otp-box — promoted to fit-ui.css if it recurs in 3rd prototype).

iOS ref: shared OTPCodeInputView component (also used in phone signup).

  • States: empty / filled / focused / error — visible via class modifiers on au-otp-box.
  • Auto-submit: when all 6 digits filled and pass server check, auto-advances to step 3 — no need to tap Verify.
  • Resend timer: button is disabled with "Resend in 0:42" countdown for 60 sec after each send. After timer elapses, button enables: "Resend code".
  • Server errors: 401 wrong code → red border on all 6 boxes + small error text "Code doesn't match — try again"; 410 expired → "Code expired — request a new one" + auto-enable Resend.
  • Paste support: pasting 6-digit string into any box auto-fills all 6.

Forgot password · step 3 — new password

Final step: set a new password. Same password-rules list as sign-up. On Save → backend updates credentials, signs user in automatically, lands on main app.

iOS ref: Authentication/ForgotPassword/ForgotPasswordView.swift (newPassword state).

  • Single new-password field (no "Confirm new password") — eye-toggle covers the typo-prevention use case + reduces friction. Server hashes whatever's submitted; if user typo'd, they'll Forgot Password again. Same approach as account-access.md change-password.
  • Rules list reuses page-local au-pw-rules / au-pw-rule from sign-up email form.
  • CTA copy: "Save and sign in" — single action that does both. No separate sign-in step after.
  • OTP token from step 2 is short-lived JWT in client memory, sent in the Save request body. Backend verifies before applying password change.

In production, this also revokes all existing sessions on the account (per account-access.md security model). Old phones / tabs signed in get logged out within 60 sec.

Phone · enter number

After email/password sign-up succeeds, user must add and verify a phone number to continue. Phone is not a login credential per authentication.md § 2026-05-11 update — it's an outreach attribute used for booking reminders, SMS notifications, and account recovery. It's never shown to other users.

iOS ref: Authentication/PhoneNumber/Set/SetPhoneView.swift.

  • Single composite input: canonical fit-input-group + fit-input with a tappable country chip (page-local au-phone-country, mirrors pf-country in account-access) + phone number input.
  • Country chip tap → push to s-country-picker (re-used screen).
  • Default country: device locale (Georgia +995 in the prototype as it's the most common dev locale; production picks from NSLocale.regionCode).
  • No "Skip" — phone capture + OTP verification is mandatory at signup (decision 2026-05-19). Account remains unusable until phone is verified; if user kills the app mid-flow, signin resumes here.
  • Backend: POST /signup/phone sends a 6-digit OTP via Twilio.

Phone uniqueness: NOT enforced — per authentication.md § 2026-05-11 update, same phone can be on multiple accounts (family / shared device). No "phone already in use" error.

Back chevron in the prototype is for navigation convenience. In production, after email signup the account is provisioned server-side as phone_verified: false — going back doesn't unwind the account creation. Back chevron may be hidden or repurposed as "sign out" in iOS.

Phone · OTP code

Verify phone ownership. Same OTP component pattern as forgot password (au-otp-boxes / au-otp-box) — promoted to fit-ui.css when a 3rd consumer appears.

iOS ref: shared OTPCodeInputView + SignUpWithCredentialsView.codeEntry state.

  • States: empty / filled / focused / error (same as forgot-otp).
  • Auto-submit: when 6 digits filled — fires Verify automatically.
  • Resend timer: 60s disabled then "Resend code". Twilio costs / SMS-pumping protection.
  • "Use a different number" footer link — returns to phone entry. Useful when typo / wrong country / etc.
  • Server errors: 401 wrong code → red border + small error; 410 expired → reset code; 429 rate-limit → banner with retry-after.

On successful verify → user account becomes "phone-verified" (cosmetic flag for now; later used for in-person bookings where coach wants to call the athlete). Lands on onboarding wizard (next batch of prototypes).

Country picker

Re-used screen for any flow that needs to pick a country / dial code. Currently the only consumer in this prototype is the phone signup chip. Same screen is also re-used in account-access (change phone) and in Personal Data (home country) on prod, but those use different file copies — see promotion note below.

iOS ref: Authentication/PhoneNumber/CountryCode/CountryCodeView.swift.

  • Header: × close (not back chevron, per feedback_back_vs_close — this is a modal picker, not a push-nav step).
  • Sticky search at top (au-cp-search) — searches by country name or dial code (e.g. "+995", "geo").
  • Popular section first — top 4 markets by user base (Georgia for our launch market). All other countries A-Z below.
  • Selected row: teal check icon on the right + brand-color dial code.
  • Generic country.row data-a11y-id for ALL rows (per feedback_a11y_naming — dynamic lists use generic ID, Maestro discriminates via text:).

Promotion candidate: the au-cp-* classes here are page-local mirrors of cp-* in account-access.html. When the 3rd consumer (Personal Data home country) lands, promote to lib/fit-ui.css as fit-country-row / fit-country-group + add spec to design-tokens/docs/components.md as FitCountryPicker.
