Welcome / Role pick

Entry screen for first-time install. Two ways forward: I'm a Coach (primary gradient) or I'm an Athlete (outlined). Role is captured client-side and threaded through to sign-up / sign-in so server knows which onboarding to assign.

iOS ref: Authentication/Role/ChooseRoleView.swift (background image + welcome icon + 2 stacked buttons).

  • No back/close — this is the root of the unauthenticated stack.
  • Sign-in path: tap "Have an account? Sign in" — to be added on sign-up entry screen (next).
  • Returning users skip this entirely — auth state restores from keychain → goes straight to last role.

Background image (welcome-background asset on iOS) intentionally simplified here — prototype focuses on layout + interaction. Real asset lives in Resources/Images.xcassets/Authentification/welcomeBackground.

Sign-up · method picker

3 sign-up methods stacked: Email (primary), Apple (black pill), Google (white-ish outlined). Order: Email first because it's the explicit / least friction-y path; Apple second for iOS, Google third. Apple stays on iOS only (hidden on Android in production).

iOS ref: Authentication/SignUp/SignUpView.swift + AuthenticationAvailableTypes enum (`apple`, `google`, `emailOrProne` legacy typo).

  • Last-used method indicator (not shown yet) — under whichever provider was last successful on this device, render a teal-dot "Last used" caption. See sign-in screen (next batch).
  • Apple / Google buttons trigger native OS bottom sheets — no in-app screen for those flows.
  • "Have an account? Sign in" at footer — toggles into sign-in entry (next batch).

Phone is NOT a sign-up method as of 2026-05-11 per authentication.md. Phone is an outreach attribute, captured separately during signup for ownership verification (next batch).

Sign-up · email form

Email + password form. Validates client-side, posts to backend, advances to phone OTP step (next batch).

iOS ref: Authentication/SignUpWithCredentials/SignUpWithCredentialsView.swift (states: emailEntry → phoneEntry → codeEntry).

Field validation

  • Email — keyboardType: emailAddress, lowercase, RFC-5322 lite regex. Submit-on-Next moves to password.
  • Password — isSecured with eye toggle. Validator: ≥8 chars + at least one digit + at least one letter (server is source of truth per account-access.md).
  • Sign up button — disabled until both fields valid. Disabled state = 0.5 opacity + no tap.

Server errors — generic inline banner above Submit (auth-form-error). 409 email-taken → "This email is already in use. Sign in instead?"; 400 bad password → "Password too weak — 8+ chars, mix letters and digits."

Keyboard flow per feedback_keyboard_behavior: Email field Next → Password field Go → fires Sign up.
