Assistant entry points — WIP

A scratch module, not a home. Everything here is a proposal: once it settles, each screen moves to the module it really belongs to (chats → a role tab, the drawer → athlete/calendar.html, the menu item → coach/clients.html).

Athlete

Chats — the centre tab

The assistant is a correspondent, pinned at the top of the conversation list, and the tab is the history of every session you started elsewhere. That only works because most sessions do start elsewhere — from a drawer, from a client card — so the tab is where you come back, not where you begin.

Consequence: the Messages icon in the Dashboard header goes away. Two doors into one room is the mistake we already made with the bell and the Inbox. This contradicts specs/messages.md (Approved), which puts messaging in the header and explicitly rejected a nav tab — the spec has to change with the decision.

Open: one eternal assistant thread (drawn here), or one thread per context? Per-context threads make it easy to return to “that Tuesday question” but turn the list into a machine’s scratchpad.

Athlete

Event drawer — circle actions

This is the existing drawer (athlete/calendar.html#ath-event-sheet) with one change: the footer buttons become a circle row. Everything above stays — status header, the Request pill, the message icon (available in every state, that is why it lives up there) and … with Edit details.

Adding Ask AI settles the pattern. If the assistant is always offered, a drawer never has fewer than three actions — so “wide buttons below three, circles above” has no cases left. Simpler and truer: the event drawer always uses circles. Wide buttons keep the job they are actually good at — confirmation sheets, where there is one decision and a way out.

Colour is the hierarchy, so it is rationed. Exactly one gradient (the expected answer, under the thumb), exactly one red (destructive, farthest from it), everything else the same neutral plate. Ask AI is that neutral plate with a brand outline — a third fill would turn four actions into four warnings, and asking is not a decision anyway.

Not resolved: the reference had both Replan and Schedule. Our vocabulary has one — Reschedule — and two calendar-ish actions side by side read as the same thing twice, so only one is drawn.

Athlete

Assistant with context

Three things make this more than a chat box:

1. The context is visible. The request is pinned as a card, not slipped into a hidden prompt. If you cannot see what it was told, you cannot trust what it says.

2. It opens with questions, not a blank field. Suggested openers are the difference between a tool and a text input.

3. It can finish the job. The assistant has the tools, so the answer ends in Accept anyway / Ask Diana for 15:00 — and the result block says exactly what happened to the held slot. An assistant that can only advise sends you back to the drawer, and nobody comes back twice.

Cost: acting means the assistant needs the same permissions and the same guardrails as the UI — every backend rule (holds, 24h policy, who may accept) has to be enforced server-side, not in the prompt.

Coach

Entering from a client card

The other kind of context: a person rather than an event — “how is Anna doing?”, “when does her package run out?”, “draft a note about the session she missed”.

The card here is the real one (coach/clients.html#s-client-detail), cloned with its header, identity, group pills and stats. The proposal is a single row in the … menu that is already on that screen — nothing else changes.

It goes in the menu rather than the header because the header already carries Message and …, and our rule caps it at two. That also keeps the assistant out of the way for coaches who never touch it.
