Locked model the settled decisions everything below obeys — spec §2
Prepaid, straight to coach
Full amount on purchase, paid to the coach — platform holds nothing. Booking burns 1 credit, no charge at booking. Escrow considered & rejected (card would become worse than cash for the coach).
Cash or card
Card → credits active instantly. Cash → pack reads Pending until coach marks received, but credits are bookable right away (he approves every booking anyway). No redeem gate.
No expiry · refund = coach's call
Credits never lapse (sidesteps gift-card law). Refund of unused is not a platform mechanism — we hold no funds. Said plainly in the buy sheet, not implied as a guarantee.
1 type · max 3 tiers · FIFO lots
A pack = N sessions of one template, ≤3 tiers. Repeat buys stack as separate lots; credits burn oldest-first. Low-balance nudge to both sides at 20% left.

Proposed data model spec §8.1 — a PROPOSAL, not ratified against the live backend (see blockers)
package_offer
Coach's product.
coach_id, training_session_id (template), status
package_tier
Max 3 / offer. No expiry.
sessions_count, total_price{amount_minor, currency}, sold_count
package_credit_lot
One purchase. Multiple / type.
sessions_total/_used, payment_method, payment_status, price
package_redemption  ·  the burn
Booking a session burns 1 credit from the oldest active lot (FIFO), linked to the training event — no charge at booking. Cancel / decline / 48h-expiry returns the credit to the lot it came from (FIFO preserved). Booking-confirm endpoint is extended additively to accept "pay with pack credit" — never a breaking change. Money on the wire = {amount: int minor, currency}.
What still blocks it spec §9 — resolved items written into owning specs; these remain
🔴
Legal check — the only hard blocker. Two narrow questions for a lawyer: (1) may we sell prepaid packs with refund at the coach's discretion given the EU 14-day withdrawal right? (2) is the platform jointly liable for non-delivery when it processed the payment? If either is unacceptable → fall back to timed escrow (~14d) or caps + rolling reserve (both designed, neither built).
🔴
Chargeback ownership. We are merchant of record (funds flow through us, coach paid out by us) ⇒ disputes land on the platform, with zero revenue to offset (subscription, no take rate). A risk to accept knowingly — no backend task.
⚙️
Backend model not ratified. §8 is a proposal — confirm entity shapes + FIFO redemption & FIFO return with the backend before creating issues. Audit poly-backend code + docs vs this spec first.
📋
Athlete → coach report / dispute channel doesn't exist. Not a packages feature (an athlete can't report any coach today), but prepayment makes it urgent. It does not return money. Likely its own spec.
📋
Coach aggregate pack revenue. Sales-stats widget removed for now — revisit whether/where the coach sees total pack income (per-pack lifetime is on the History header).
