Coach

Clients | Lists

A list is a named set of clients — app accounts and CRM contacts side by side, exactly like the participants of an event (the add-participant endpoint already keys off relationshipId, so both kinds go down one path).

  • Why a segment and not filter chips. Chips promise “filter what’s on screen”; a list has a name, a chat and its own actions — that’s navigation, not filtering. The pane split matches the pattern we already run in sessions.html (Sessions | Packages): a thing, and the thing built out of it.
  • Smart lists live in the same pane — same card, same detail screen, only the membership is computed instead of hand-picked. That kills the second metaphor: everything here is a list, some just fill themselves.
  • No separate “filter clients by list” — opening a list already IS the filtered view of those people.
  • Card shows the avatar stack, how many aren’t in the app yet, an unread badge when its chat has news, and the series it feeds if attached.
  • Empty state keeps the smart lists visible — a coach who never builds a list still gets “who owes me” on day one.
Smart lists & data

All five come from signals we already have

Owes money ← unpaid cash sessions (the €X owed badge). New this month ← relationship date. Package running low ← the same rule that drives the amber pack footer. Not in the app ← athlete_account_status = crm. Inactive 30 days ← no events in the window. Zero new data, one new entity.

Backend

New client_list + membership keyed by relationship_id (so CRM and app rows behave identically, as in POST /coach/training-events/{id}/participants). Smart lists are server-side queries, not stored membership.

Entry points

Header “+” on the Lists pane → New list. Also planned: “Save these 8 as a list” from a group event roster, and a “put them in a list” step at the end of contact import — both reuse people the coach already gathered.

List detail

Summary, then the four things a list is for, then who’s in it. Three of the four actions hand off to flows that already exist — this screen mostly wires them to a set of people instead of one person.

  • Add to a session → the event picker, with the list pre-expanded.
  • Message the list → the group chat. Created lazily on first tap, not at list creation — otherwise Messages fills with empty threads from lists made only to schedule.
  • Invite N to the app → the existing invite flow; accepted invitees fall into the chat by themselves.
  • Attach to a recurring series — the payoff. Every date the engine generates 60 days out arrives with these people already on the roster, as coach-added: auto-accepted, fee owed, settled after the session.
  • Members — tap a row for the client card; Edit reveals remove buttons. Blocked and deleted clients drop out on their own; archived stay visible but greyed and skipped by list actions.

Lists are coach-private. Athletes never see them — the only visible consequence is the chat they get added to.

Coach

Smart list detail

Same screen shape as a manual list, minus everything that implies hand-picked membership: no Add, no Edit, no attach-to-series. The note says out loud where the membership comes from and how people leave it.

  • Actions match the meaning. “Owes money” gets a per-row Mark paid (the existing settlement action) and a total; “Not in the app” would get bulk invite; “Package running low” the renewal offer that already exists on the pack card.
  • Deliberately no group chat. A thread called “Owes money” would be a debt-collection room — nudging belongs one-to-one, from the client card.
  • Marking someone paid removes them from the list on the spot (snackbar, count drops) — that’s the whole point of a computed set.

Create list

Name + multi-select over all clients. The row component is the one from contact import (imp-) — same checkbox, avatar, tag grammar, so “pick people” looks the same everywhere in the app.

  • CRM contacts are selectable and badged — a list is not an app-users-only club.
  • Blocked / deleted are disabled at the source rather than silently filtered later.
  • Footer CTA carries the count, so the coach can commit without scrolling back up.
  • No “create a chat too?” toggle — the chat appears when it’s first needed.
Coach

List chat

The group thread from shared/messages.html, unchanged — only the two states that lists introduce are drawn here.

  • Membership mirrors the list. Added to the list → added to the chat, with a system line so nobody wonders who the new person is. Removed → removed, same line. Half-mirroring would need explaining; full mirroring doesn’t.
  • CRM members can’t be in it — DM is between connected accounts, and they have none. The plate above the composer states the gap and offers the invite instead of silently dropping three people.
  • Renaming the list renames the thread. Deleting the list keeps the thread — the conversation belongs to the people in it; it just stops following the list.
  • Header says “follows the list” so the coach knows this thread has an owner, unlike an ad-hoc group.

Event picker with lists

Extends the shipped picker (calendar.html#s-invite) with a Lists section above the flat client list. Same rules as before: everyone added is auto-accepted and owes the fee, settled after the session.

  • List row = one checkbox for everyone, chevron expands to per-person control. Bulk without losing the ability to drop one person.
  • Members already on the roster show In session and are disabled — adding a list twice is harmless.
  • Over capacity doesn’t block. Amber note with the exact overflow; the coach deselects or raises the event limit. Same stance as skipped occurrences when publishing a series.
  • The by-link row stays at the bottom for people who aren’t clients at all.
