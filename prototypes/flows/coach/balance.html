Earnings

Cash state
Card / Stripe state

Earnings — coach-side of money, two independent income streams shown as swipeable cards. Default visible: Cash (always active, every coach gets some). Swipe right → Card (via Stripe). Why Cash default: works from day 1 with zero setup; Stripe is the upgrade path, not the prerequisite.

  • Cash card — "Received this month" + "Owed by N athletes" tappable row that deep-links to Clients filtered to outstanding cash.
  • Card card — 6 substates mirroring Stripe Connect lifecycle: Lock (CTA to connect) / Verifying / Action required / Zero balance / Active / + Instant (post-MVP premium).
  • Peek + dots — 12px of next card visible on the right edge + two dots under the swiper signal the swipe affordance; tapping a dot scrolls there.
  • Recent activity — unified across cash + card with data-method badge per row. Filter chips above (All / Cash / Card / Payouts) narrow the list client-side.
  • Lifetime footer — "This month €600 · €2,840 lifetime with 321Fit" replaces the older single-number celebratory line.
Full behavior spec

Why Cash default

Cash works for every coach from day 1 (no Stripe setup, no KYC). Defaulting to Cash inverts the empty-state problem — new coaches see something useful immediately rather than a "Connect Stripe to see your money" wall. Stripe is positioned as the upgrade ("Accept card payments too"), not the gate. Coaches with active Stripe lose one swipe gesture.

Swiper mechanics

CSS scroll-snap on the track (scroll-snap-type: x mandatory), each card is flex: 0 0 calc(100% - 40px) — leaves 12px peek of the next card. Scroll listener updates dot indicator on idle; dots are tappable to programmatically scroll. Native momentum on iOS via -webkit-overflow-scrolling: touch.

Cash card states

Active: "Received this month €120" + "€40 owed by 2 athletes →" link. Zero: empty-state copy "No cash collected yet — mark sessions paid in Clients to track here". No CTA on the card itself — entry to Mark Paid lives in Clients / Session detail.

Card / Stripe card states (6)

Lock: empty + primary CTA "Connect Stripe" → pushes to #s-stripe in Not set up state.
Verifying: info banner "Stripe is verifying" + tappable row "View details" → #s-stripe Verifying.
Action: warn banner "Action needed: Proof of address" + primary CTA "Resolve now" → #s-stripe Action required (reopens SDK to the missing requirement).
Zero: Available / Pending = €0.00 muted + "Finish your first card session to start earning".
Active (MVP): Available / Pending split + "Next payout · Mon, Apr 27".
+ Instant: same + "Withdraw" pill with Premium tag + post-MVP notice banner below the swiper.

Method badges + filter chips

Each .earn-txn carries data-method="cash|card|payout". Filter chips set data-filter on the txn group; CSS hides rows not matching. Cash/Card badges visible inline next to txn title for at-a-glance scanning when filter is "All". Payouts row has no inline badge — identifies itself via icon + title.

Hold period (unchanged)

Card earnings enter Pending on session complete. After 24h (no refund/no-show), they move to Available. Tap on Pending label → existing pending-info sheet explains the timeline.

Minimum payout threshold (unchanged)

Auto-payout fires only when Available ≥ €20. Below — rolls to next Monday.

Lifetime footer

"This month €600 · €2,840 lifetime with 321Fit" — sums Card available + Cash received (this month) + lifetime equivalent for lifetime. Hidden when both are 0 (brand-new coach has nothing motivational to show yet).

API (extended)

GET /coach/earnings/ — new shape: { available, pending, currency, payoutSchedule, defaultProvider, cashOwed: { count, total }, cashReceivedThisMonth, totalIncomeThisMonth, lifetimeTotal }
GET /coach/transactions/?limit=4&method=cash|card|payout — preview for Recent activity, optional method filter
POST /coach/payout/instant/ — triggers Stripe Instant Payout (post-MVP, premium)
Stripe Connect onboarding: see stripe-connect-onboarding.md

Backend gap

Currently coach balance is computed on-the-fly from completed events. Needs real coach_balance table + append-only coach_transactions ledger with explicit method column. See project_coach_balance_decisions.md.

Coach

Cash earning detail

Per-session detail for a cash earning. Same scaffolding as the Card variant (hero + session + payment) but with cash-specific semantics: no 24h hold, no payout reference, no platform fee — just «has the athlete handed over the money yet?»

State machine: after the cash session is marked Finished, the txn starts as Unpaid. Coach taps Mark as paid → transitions to Received. Terminal — no Mark-as-unpaid reverse action (mistakes go through Support; keeps the audit trail clean).

  • Unpaid — session done, athlete hasn't handed over the money yet. Hero pill is yellow ("Unpaid"). Info banner explains why we can't auto-track. Primary CTA Mark as paid.
  • Received — coach already marked it paid. Hero pill is teal ("Received"). "Marked paid" timestamp shown in Payment section. No bottom action — terminal state.

Entry points: tap any data-method="cash" txn in Recent activity, or tap an athlete in Clients → Cash owed list (filter on Clients screen, future spec). Both routes land here.

Mark as paid flow: in prototype the button directly toggles state for demo. In production: bottom sheet confirm ("Confirm Anna paid €30 in cash?") → backend creates cash_paid ledger row → toast "Marked as paid" → screen re-renders in Received state.

Coach

Earnings history

Unified earnings history — one screen for "how much did I earn each month" across Cash + Card (+ future providers). Built on existing patterns: .earn-detail-hero for lifetime, .earn-section per year, .earn-kv-group for month rows.

  • Entry points (3): tap Cash card top (filter = Cash), tap Card card top (filter = Card), tap lifetime footer (filter = All).
  • Filter chips mirror the entry: pre-selected based on which card opened it; user can re-filter without leaving.
  • Month rows show one total (right) + (on All filter) breakdown subline below the month name. Currently read-only — see "Month drill-down" note below.
  • Current month highlighted in teal with "· current" suffix; signals "this is what's still accumulating".
  • Year separators (2026 / 2025) using .earn-section-head + .earn-section-title.

Why a separate screen vs Transactions? Transactions is a flat ledger (individual events). This screen is an aggregated summary (per-month totals). Different purposes — the coach asks "how much did I make in March?" not "show me every transaction in March".

Month drill-down (deferred decision): Transactions screen has no month filter today. Two paths to enable drill-down:
  A. Add a month filter chip to Transactions (small change — chip appears at top with "April 2026 ×" when arriving from here). Cheapest.
  B. New Month Detail screen showing all transactions for that month + summary card at top. More work, more focused UX.
Until decision — month rows are read-only (no chevron, no tap). Annotation lists this as the open item.

Lifetime calculation: shows net earnings (gross minus refunds, disputes, fees). What landed in pocket / bank, not what was originally invoiced. Backend computes from coach_transactions ledger filtering on net-affecting types.

Future: small bar chart at top above filter chips (last 6 months as bars, current highlighted) once we have enough data to make it meaningful.

API

GET /coach/earnings/history/?from=YYYY-MM&to=YYYY-MM&method=all|cash|card — returns { lifetime: {total, card, cash}, months: [{year, month, total, card, cash, sessionCount}...] }

Interaction details

Empty state

Coach has no payout accounts connected yet — reached from Earnings Needs payout method CTA. Each provider shows inline "Connect" action. Tapping Connect on Stripe launches the StripeConnect embedded component (native iOS SDK, not WebView) — form lives in-app, validation + doc upload + selfie verification all native.

After Stripe webhook fires account.updated with charges_enabled & payouts_enabled → backend creates PayoutAccount with is_default=true → user returns to Single (MVP) state. If webhook reports requirements.currently_due non-empty → Stripe screen shows Action required.

Single state (MVP)

Only Stripe connected, no radio (default is implicit), ⋯ menu has only Disconnect. Revolut is a "Coming soon" placeholder to show provider abstraction intent.

Multi state (future)

2+ methods connected. Each card has an iOS-style radio on the left. Tapping empty radio = instant switch (toast "X is now your default"). Tapping filled radio does nothing. "Set as default" in ⋯ menu is hidden when the method is already default.

Disconnect behavior

Backup exists: soft confirm sheet — "Your next payout will go to {fallback}". Destructive red CTA.

Only method: warning sheet — yellow triangle + "Payouts will be paused until you add another method — your earnings will stay on hold". Explicit tradeoff. User can still proceed (not blocked). On confirm → falls to Needs-payout-method state on Earnings screen.

API

GET /coach/payout-methods/ — list (returns {} for empty state)
POST /coach/payout-methods/stripe/session/ — returns {client_secret} for embedded onboarding component
PATCH /coach/payout-methods/{id}/ {is_default: true} — switch default
DELETE /coach/payout-methods/{id}/ — disconnect (backend must re-route default to next available; pause payouts if none left)

Coach

Stripe Connect

Refactored 2026-06-02 — in-app control center. No more "Manage on Stripe" WebView redirect. The Connected state hosts the full payout management UI (banks, withdraw, history, disconnect). Four lifecycle states reflect the Stripe Connect Custom account.

  • Not set up — intro + checklist + legal consent checkbox → Start setup pushes to #s-stripe-onb-confirm (native 3-step flow). Country / Business screens dropped (auto-filled from profile).
  • Verifying — info banner → Continue setup reopens the same onb flow at the right step.
  • Connected — full in-app control: account meta + bank accounts list (multi) + payout block (Available + Next payout always visible) + manual mode toggle + activity preview + Disconnect.
  • Action required — warn banner + missing items → Resolve now deep-links to the failing onb step (usually #s-stripe-onb-id when Stripe asked for additional docs).

Legal consent (Not set up only): coach must check the consent box before "Start setup" enables. Three agreements bundled: 321Fit Terms, 321Fit Privacy, Stripe Connected Account Agreement. Stripe Services Agreement itself is accepted inside the SDK on the final onboarding step — not our concern. On tap of enabled "Start setup": client posts POST /coach/stripe/consent with consentVersion, then fetches account_session and opens StripeConnect.AccountOnboardingController.

iOS native SDK: uses StripeConnect module — not WebView. Native controller rendered in-app. Backend creates account with controller.stripe_dashboard.type = none (required for full embedded UX; Express redirects to Safari mid-flow).

Integration plan

iOS

StripeAPI.shared.publishableKey = ...
let mgr = EmbeddedComponentManager(fetchClientSecret: ...)
let vc = mgr.createAccountOnboarding(...)

Backend

POST /coach/stripe/consent — records { acceptedAt, ip, consentVersion }. Must succeed before next call.
POST /coach/stripe/account-session/ — returns { client_secret, publishableKey } for embedded components. Returns 409 consent_required if consent missing. Replaces current /coach/stripe-onboarding redirect URL.

Account creation

Backend creates Connect account with controller.stripe_dashboard.type=none, controller.requirement_collection=stripe, capabilities card_payments + transfers. Express (type=express) is incompatible — some onboarding steps redirect to Stripe-hosted Safari pages.

State mapping

Stripe webhooks → update PayoutAccount.status: none → pending → done. Action-required triggered by requirements.currently_due becoming non-empty. Earnings screen's Stripe preview card mirrors this automatically.

Existing Express accounts

<5 coaches on legacy Express — reset stripeConnected=false on next deploy; each coach re-runs onboarding under new type=none controller. No data migration; old Stripe accounts left dormant.

Disconnect entry points

Coach can reach Disconnect either via ⋯ menu on the method card in Payout methods list, OR via the destructive button on the Connected state of this Stripe detail. Both open the same warning sheet — 3 variants now: clean (nothing pending), pending-balance (positive balance → suggest Withdraw first), active-events (future card-paid sessions → refund warn).

Stripe Onboarding — Confirm info

DOB variant

Step 1 of 3. Single review screen showing everything from GET /stripe-onboarding/prefill. Split into two sections:

  • Auto-detected (locked) — name / email / phone / country. Lock icon + caption "To change locked fields, edit your profile in Settings." Source = auto in prefill response.

Why not split into 2-3 screens? All fields fit on one scroll. Adding stepper screens for fields the user usually just confirms = pointless friction. iOS impl should still keep this single screen even when DOB is missing (the inline picker takes less vertical room than a separate step).

Bank role

Withdraw

Manual withdraw screen — only reachable when Manual payouts toggle is ON. Large amount input + 3 quick chips (€50 / €100 / All). Destination = current default bank. Below-minimum (< €20) shows warn banner + disables Confirm. ETA copy below input ("1–2 business days; first payouts may take longer").

  • Confirm → POST payout → success toast → back to #s-stripe with refreshed Available.
  • Stripe minimum (€20) enforced client-side + server-side.
  • Multi-bank: tap Destination row to switch (future — v1 always uses default).

API

POST /coach/stripe-onboarding/payout body {amount, currency}. Returns {payout_id, status, arrival_date}. Failure cases: insufficient_funds, account_not_verified, external_account_required.

Coach

Payouts history

Lifetime payouts list, grouped by month. Lifetime summary card at top. Each row: destination + date + status (Completed / In transit / Failed · retried) + amount. Tap → reuses existing #s-txn-payout detail screen.

  • Status colors: Completed = teal, In transit = blue, Failed = red.
  • Failed payouts that auto-retried successfully show "Failed · retried" with original date but final amount.
  • Pagination: 20 per page, load-more on scroll bottom.

API

GET /coach/stripe-onboarding/payouts?limit=20&before=<cursor> → returns { items: [{id, amount, currency, status, arrival_date, destination_last4}], next_cursor, lifetime_total }.
