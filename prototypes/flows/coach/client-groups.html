Coach

Clients | Groups

A group is a named set of clients — app accounts and CRM contacts side by side, exactly like the participants of an event (the add-participant endpoint already keys off relationshipId, so both kinds go down one path).

  • Why a segment and not filter chips. Chips promise “filter what’s on screen”; a group has a name, a chat and its own actions — that’s navigation, not filtering. The pane split matches the pattern we already run in sessions.html (Sessions | Packages): a thing, and the thing built out of it.
  • Smart groups live in the same pane — same card, same detail screen, only the membership is computed instead of hand-picked. That kills the second metaphor: everything here is a group, some just fill themselves.
  • No separate “filter clients by group” — opening a group already IS the filtered view of those people.
  • Card shows the avatar stack, how many aren’t in the app yet, an unread badge when its chat has news, and the series it feeds if attached.
  • Empty state keeps the smart groups visible — a coach who never builds a group still gets “who owes me” on day one.
Smart groups & data

All five come from signals we already have

Owes money ← unpaid cash sessions (the €X owed badge). New this month ← relationship date. Package running low ← the same rule that drives the amber pack footer. Not in the app ← athlete_account_status = crm. Inactive 30 days ← no events in the window. Zero new data, one new entity.

Backend

New client_group + membership keyed by relationship_id (so CRM and app rows behave identically, as in POST /coach/training-events/{id}/participants). Smart groups are server-side queries, not stored membership.

Entry points

Header “+” on the Groups pane → New group. Also planned: “Save these 8 as a group” from a group event roster, and a “put them in a group” step at the end of contact import — both reuse people the coach already gathered.

Group detail

Everything on this screen is a row. The previous pass wrapped each action in a card with a two-line description and each session in another card — ~200px spent on things a coach does daily and already understands. Rebuilt on the grammar every messenger and contacts app uses for a set of people.

  • Actions moved to their canonical homes. Chat → icon in the header (with the unread count, like any thread). Scheduling → the footer CTA, because it’s the one thing a group exists for. Rename / Delete / Add / Edit → ⋯. No action cards at all.
  • No identity strip. The avatar row on top restated the member list two sections below it; the count moved to the Members header, where the people actually are.
  • Edges are hybrid, matching session-detail.html: things that group get one 1px outline — the schedule block holds its rules, its one-off dates and the See-all row inside a single contour, exactly like a series holds its instances there. Things that are just a list of people stay bare on the canvas. A slab around eight members reads as a wall; a contour around the schedule gives the page its edge. (Dark = hairline on transparent, light = white + soft shadow.)
  • Schedule separates the two kinds it used to blur. Both rows lead with the session name, then when: a rule (repeat icon) reads days · time and a third line with the next date; a date (calendar icon) reads date · time, no weekday — the weekday is noise once an exact date is given. No spots count here — the whole group is assumed on it; fill belongs to the event. Rules are always all shown — they’re few and they explain everything else; one-off dates are capped. Toggle the second state above to see a busy group (2 rules + 2 one-offs).
  • See all N dates opens the group’s own schedule screen, not the calendar — the calendar would drop the coach into a wall of everything, losing the group context they were just in.
  • Add clients is the first row of the member list — the WhatsApp/Telegram convention: a plus where the next avatar would be. It’s also in ⋯, and it hides while the list is armed for removal.
  • Members are never truncated. The list is the point of the screen; making a coach tap “see all” to view their own group would be silly.
  • Edit: the whole row removes, rows tint red while armed, and every removal lands a snackbar with Undo — that’s what makes a big destructive target safe.
Scheduling a group

No new mechanic

“Schedule a session” enters the shipped flow — invite.html?mode=schedule → session chooser (filtered to group templates) → drop on the time grid → post-drop drawer. The group only pre-fills the roster. Sidebar “Schedule drawer” opens the last step.

The drawer stays the canon pair

Just this date / Repeat weekly (day chips + Ends), exactly as it ships today, plus one line of consequence: all 8 land auto-accepted with the fee owed, CRM contacts included, settled after the session. The earlier “add to an existing series” option is gone — the group was already chosen a step earlier, so it answered a question nobody asked.

Where the roster is edited later

Per-date changes belong to the event, not the group: the event’s own Invite picker (calendar.html#s-invite) gains a Groups section. One section in that file, not a screen here.

Group schedule

Every date this group is on, in one place. Same shape as the series detail in session-detail.html, because the question is the same — when does this run? — only the filter is the group instead of one placement.

  • Repeats first. The rules explain most of the rows below, so they sit on top with how many dates each one contributes inside the 60-day generation window.
  • Dates grouped by month, each row carrying its source icon (repeat vs one-off), the session name and the fill. A group with two series and two one-offs interleaves them chronologically — that’s how the coach’s week actually looks.
  • One quick-chip axis: the source (All / per series / One-off), per the ledger-filter rule. Filtering empties a month card → the card hides rather than leaving a stray header.
  • Low-signup dates keep the amber count, same language as the series screen.
  • Footnote repeats the 60-day window and states the removal rule: taking someone out of the group only affects future dates.

Smart group detail

Same screen shape as a manual group, minus everything that implies hand-picked membership: no Add, no Edit, no attach-to-series. The note says out loud where the membership comes from and how people leave it.

  • Actions match the meaning. “Owes money” gets a per-row Mark paid (the existing settlement action) and a total; “Not in the app” would get bulk invite; “Package running low” the renewal offer that already exists on the pack card.
  • Deliberately no group chat. A thread called “Owes money” would be a debt-collection room — nudging belongs one-to-one, from the client card.
  • Marking someone paid removes them from the group on the spot (snackbar, count drops) — that’s the whole point of a computed set.

Create group

Name + multi-select over all clients. The row component is the one from contact import (imp-) — same checkbox, avatar, tag grammar, so “pick people” looks the same everywhere in the app.

  • CRM contacts are selectable and badged — a group is not an app-users-only club.
  • Blocked / deleted are disabled at the source rather than silently filtered later.
  • Footer CTA carries the count, so the coach can commit without scrolling back up.
  • No “create a chat too?” toggle — the chat appears when it’s first needed.

Add clients to a group

Same picker as Create, minus the name field — the group already has a name, and re-asking for it makes the coach wonder whether they’re about to make a second group.

  • Reached from the ⋯ menu (Add clients) and from the Add clients row under the member list — a full-width 60px target instead of a text link wedged next to another text link.
  • Existing members stay visible, disabled, tagged In this group. Hiding them reads as “they’re gone”; showing them answers “is Anna already in?” without a trip back.
  • Header names the target (Add to Morning) and the CTA counts (Add 2 to the group) — the same commit grammar as Create.
  • Note spells out the chat consequence: app members land in the thread immediately, CRM contacts only after they accept an invite.
Coach

Rename group

A pushed screen, not an inline field in the header and not a sheet — and it’s a straight clone of shared/messages.html#s-group-rename, which already solves this exact problem for DM groups.

  • Why not inline in the header. The header has a back button, two icon buttons and a title in ~360px; turning the title into a field leaves no room for Cancel/Save and no clear way to back out. It also diverges between iOS and Android, where inline title editing isn’t a native habit.
  • Why not a sheet. The keyboard covers the bottom of a sheet — the same reason the package tier editor is a screen (see sessions.html). Cancel/Save in the header stays reachable above the keyboard.
  • Opens focused, with the current name selected — one tap and you’re typing the new name, no cursor fiddling. Cancel discards, Save commits.
  • 40-char limit with a live counter, same as the DM group rename, so long names can’t break the header or the list card.
  • Hint states the consequence: groups are private, but the chat thread carries the name too — so renaming is visible to members through the chat.
Coach

Client → groups

Opened from the Add to group pill on the client card. The gap it closes: groups were only visible from the group side, so from a client you couldn’t see — or change — where they belong.

  • One screen adds and removes. Rows start checked for the groups the client is already in, so the screen shows membership rather than an empty add-only list. Unchecking leaves the group. Nothing commits until Save, which is what makes the two-way behaviour safe.
  • The CTA states what will happen: Add to 2 groups when you only added, Save changes as soon as a removal is in the set, plain Save when nothing changed.
  • Create a new group is the first row, above the list — same grammar as Add clients inside a group. It pushes the create screen with this client already selected, so “start a group around this person” is two taps.
  • Smart groups are absent by design — their membership is computed, you can’t hand-add to “Owes money”. Stated in the note so the omission doesn’t read as a bug.
  • The note also spells out the chat consequence, because that’s the one thing the athlete actually sees.

On the client card the groups render as pills (tap → that group) plus a dashed Add to group pill. A client in no group shows only the dashed pill — no empty section.

Group chat

The group thread from shared/messages.html, unchanged — only the two states that groups introduce are drawn here.

  • Membership mirrors the group. Added to the group → added to the chat, with a system line so nobody wonders who the new person is. Removed → removed, same line. Half-mirroring would need explaining; full mirroring doesn’t.
  • CRM members can’t be in it — DM is between connected accounts, and they have none. The plate above the composer states the gap and offers the invite instead of silently dropping three people.
  • Renaming the group renames the thread. Deleting the group keeps the thread — the conversation belongs to the people in it; it just stops following the group.
  • Header says “follows the group” so the coach knows this thread has an owner, unlike an ad-hoc group.
