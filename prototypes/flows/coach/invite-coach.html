Coach

Invite a coach (referral)

Coach-to-coach referral. Separate from coach/invite.html (which is invite an athlete to a training event). Reached from Settings root card "Invite a Coach".

States (sidebar to toggle)

UI atoms (kit-aligned)

  • .fit-avatar.fit-avatar-md.fit-avatar-brand for invitee initials
  • .fit-empty-state + -title for "No invites yet"
  • .fit-snackbar for "Link copied" / "Invite shared" confirmations
  • .sk-shimmer for loading skeleton rows

Kit candidate: FitInviteRow + FitInvitePill — reused on athlete-side referral too once landed. Will propose to kit when athlete-side flow is built.

List content (MVP)

Flat list of coaches who signed up through the inviter’s link. No status pills, no filter chips in MVP — share-link path doesn’t capture invitee contact, so “pending” / “didn’t accept” states are unknowable. CSS/JS for pills was removed to avoid suggesting capability we don’t have.

Each row: FitAvatar(.md, .brand) + name + “Joined N ago”. Most-recent-first.

Phase 2 — when to bring back status pills

Two triggers, either one unlocks pill UI:

  • Invite-by-email path ships — coach enters invitee’s email/phone, backend creates a row with status: pending, transitions to joined on signup. Then we can render the yellow Pending pill.
  • Rewards mechanic lands — “Active” (joined + completed a qualifying session) becomes meaningful for reward eligibility. Show the teal Active pill and surface session count.

Until either lands, the list stays flat — nothing on screen that the backend can’t actually verify.

Backend contract — devs implement

Referral tracking is the load-bearing piece, not the UI.

Tables / fields:

  • referrals table: id, inviter_user_id (coach), referral_token (unique slug, used in link), invited_contact (NULL for MVP share-link path — populated only when invite-by-email lands in Phase 2), invitee_user_id (FK, NULL until signup), status, created_at, joined_at, activated_at
  • Token format jm-r3F7q9 = {first_initial}{last_initial}-{6char base62}. Globally unique. Stable per coach — same token reused across all their invites for attribution simplicity.
  • Status column reachable values (MVP): only joined on share-link path. Rows are NOT created at link-share time (we have nothing to write — no invitee contact). Rows appear only when someone actually signs up with the token.
  • Phase 2 status values: pending (invite-by-email row created at send time, no invitee_user_id yet), active (joined + first completed session). Same table, additive fields/values per feedback_backward_compat_endpoints.

Endpoints (additive — per feedback_backward_compat_endpoints):

  • GET /coach/me/referral-link → { url, token }
  • GET /coach/me/invites?limit=N&cursor=... → paginated list of joined coaches with relative timestamps. Does not include status field in response yet — adds it in Phase 2 alongside pill UI.
  • POST /referrals/track-open (called from /i/<token> public landing) — logs that someone opened the link. Optional, used for funnel analytics; never creates a row.
  • Signup endpoint accepts referral_token param → backend resolves to inviter, creates the referral row with status: joined, invitee_user_id set.
  • Phase 2: first-completed-session hook flips status → active, fires push notification to inviter (TargetRoute=REFERRAL_ACTIVATED).

Rewards mechanic intentionally NOT in MVP scope per project_invite_a_coach memory (2026-04-22). Track all data now; reward UX comes Phase 2 once we see traction. Hero subtitle copy "we’ll track who joined through you for future rewards" sets expectation without committing.

Share flow

  • Copy button → JS clipboard API + snackbar "Link copied" 1400ms
  • Share invite link CTA → native OS share sheet (iOS UIActivityViewController, Android Intent.ACTION_SEND). On platforms without share API, falls back to mailto / WhatsApp deep-link with pre-filled text.
  • Pre-filled share text: "Join me on 321Fit — the marketplace for coaches and athletes. {link}"

See all invites

Inline list shows last 3 by default. See all invites link pushes to s-invite-coach-list — full paginated list with sticky filter chips (All / Pending / Joined / Active) at top.

Edge cases

  • Invitee self-signs with different email than what you tracked — backend matches on referral_token, not contact info.
  • Invitee was already a member when they opened the link — show benign message on landing page "Welcome back", no referral linked.
  • Coach deletes account — referrals stay; inviter_user_id may be soft-nulled with anonymous label.
Coach

All invites

Push screen — full list of coaches who joined through this inviter’s link. Reached from See all invites at the bottom of the inline list on s-invite-coach.

Layout (MVP)

  • Header: back chevron + “Your invites”.
  • Flat scrollable list — .ic-invite-row atom: avatar + name + “Joined N ago”. No pills, no filters.
  • Sort: most-recent-first (joined_at desc on backend).

Pagination

  • Cursor-based, limit=20 per page.
  • Infinite-scroll trigger 200 px before end. Loading-more indicator at footer (spinner only, no skeleton).
  • Endpoint: GET /coach/me/invites?limit=20&cursor=...

Empty

If list is empty, the push screen isn’t reachable — See all invites link is hidden on the main screen when count is 0. So empty-state handling lives on s-invite-coach, not here.

Phase 2 additions

When pills come back (see main-screen annotation): add sticky filter row with 4 chips (All / Pending / Joined / Active), each showing counts. Server adds ?status=<filter> param. Same row atom gains a trailing pill via .ic-invite-pill--{status}.

Prototype shows 9 sample joined coaches so scroll is meaningful for testing. Production list pulls from GET /coach/me/invites.
