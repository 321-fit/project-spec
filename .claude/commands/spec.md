# /spec — Issue generator from product specs

You are a project manager assistant for 321Fit. Your job is to break down approved product specs (from `project-spec/specs/<module>.md`) into actionable GitHub issues across the relevant repos, add them to Project #2, and apply consistent labels and assignees.

Argument: `$ARGUMENTS` — the spec file name without extension (e.g. `dashboard`, `group-training`, `location-picker`).

---

## Step 1 — Classify the spec

Determine the spec's character based on its content:

| Type | Signal | Pattern |
|---|---|---|
| **module** | Spec describes a single screen / module touched by 1-3 platforms with parallel work | One issue per platform (`<module>` × `repo:poly-backend` / `repo:321fit_ios` / `repo:321fit_android_new`) |
| **cross-cutting / flow** | Spec describes a user journey or feature spanning multiple modules across platforms | **Epic** issue in `project-spec` + sub-tasks in each touching platform repo |
| **reusable component** | Spec is for a shared component picker / atomic UI used by multiple parent specs | One issue per platform consuming the component (or batch into design-tokens if the component itself is missing) |
| **infrastructure** | Spec is for assets, contracts, build pipeline | Single issue in `design-tokens` or `project-spec` |

Heuristic — read Implementation header in the spec:
- Lists iOS + Backend + Android implementation rows → **module** or **cross-cutting**
- Distinguish further: if Spec section "User stories" describes a multi-step journey, it's **cross-cutting**; if it's "screen behavior", it's **module**

If unsure, **ask the user** before proceeding to issue generation. Do not guess.

## Step 2 — Plan issues

Build a planned issue list. Each entry has:
- Repo
- Title (Conventional Commits style)
- Labels (must include `phase-4` + `module:<spec-name>` + `repo:<repo>`; add `epic` / `pilot` / `type:*` as relevant)
- Assignees (from `reference_team_assignees`)
- Body (full template, see Step 3)
- Project: #2
- **Integration branch (resolved)** — for each touched repo, read `<repo>/.claude/CURRENT_INTEGRATION_BRANCH` (e.g. `cat poly-backend/.claude/CURRENT_INTEGRATION_BRANCH`) and capture the current value. Embed this verbatim in Implementation order step 2/3 + Acceptance criteria of THIS issue. Per `feedback_task_creation` Branch reference criterion — agent reads file at run time (resilient to renames), reader sees current value without leaving GitHub.

For **module specs** (dashboard, payments, etc.), produce:
- 1 issue per platform repo (backend, iOS, Android — skip platforms not touched by the spec)
- Each titled `feat(<module>): <module-name> <platform-suffix>` (e.g. `feat(dashboard): dashboard backend`, `feat(dashboard): dashboard iOS`)
- Backend issue should add `type:contract` if this module introduces a new `<module>-api.md` doc (i.e. new endpoints, not just extending existing ones)

For **cross-cutting / flow specs** (group-training, vacation-mode, onboarding-wizard):
1. Epic issue in `project-spec` repo:
   - Title: `epic(<module>): <human readable feature>` (e.g. `epic(group-training): group training feature`)
   - Labels: `phase-4`, `epic`, `module:<module>`
   - Body: tracking checklist with placeholder links to sub-tasks (filled in after sub-tasks are created)
   - Assignee: leave empty (epics track, don't assign)
2. Sub-tasks in each platform repo it touches
   - Title: `feat(<module>): <module> <platform-suffix>`
   - Body line at the top: `Part of epic: 321-fit/project-spec#<epic-number>`
   - Labels: `phase-4`, `module:<module>`, `repo:<repo>` (no `epic` label on sub-tasks)
3. After all issues are created, **edit the epic body** to insert real sub-task links

For **reusable component specs** (sport-picker, location-picker, session-creation):
- Behave like module specs (1 issue per platform), but add `type:component` label if the design-tokens repo also needs a component issue
- If a design-tokens issue is needed, add it to the plan separately with `repo:design-tokens` + `type:component`

## Step 3 — Issue body template

Every issue body must be **self-contained** so a developer (human or AI agent) can pick it up and work autonomously without further questions. Required sections:

```markdown
## How to run (via OpenClaw in Mattermost)

Send to the bot in the issue thread, verbatim:

> запусти `/<architect-command> impl-doc <spec-name>`

Where `<architect-command>` is:
- `architect` for `repo:poly-backend`
- `ios-architect` for `repo:321fit_ios`
- `android-architect` for `repo:321fit_android_new`

The bot translates this into a Claude Code agent run with the spec name as argument. Do NOT ask the bot to "choose between impl-doc / spec / analyze" — `impl-doc` is the canonical Phase 4 command; the rest are not used for this flow.

## Cross-repo paths the agent needs

The spec and prototype live in the sibling `project-spec` repo (not the platform repo this issue lives in). The per-module API reference lives in `poly-backend/docs/<spec-name>-api.md` (see lookup order in next section):

- Spec source: `project-spec/specs/<spec-name>.md` — fetch via [GitHub Pages](https://321-fit.github.io/project-spec/specs/<spec-name>.md) if no local checkout
- Prototype HTML: `project-spec/prototypes/flows/<role>/<flow>.html` — fetch via Pages URL if no local checkout
- Design system + native theming contract: `project-spec/architecture/design-system.md`
- Legacy baseline OpenAPI (read-only, pre-Phase-4 endpoints): `project-spec/contracts/_baseline.openapi.yaml`

If only the platform repo is checked out, the GitHub Pages URLs above are authoritative — use `WebFetch` / `curl` to read them. Do not stop because local fs lacks `specs/` or `prototypes/`.

## If backend API reference is missing — DO NOT STOP   *(client-platform issues only; omit from backend issue body)*

The per-module API doc `poly-backend/docs/<spec-name>-api.md` may not exist yet at the time you run impl-doc. **This is the expected state.** The backend issue in this batch generates it in parallel via `/architect impl-doc <spec-name>` (skeleton) → `/develop implement <spec-name>` (final shapes).

**Lookup order for the agent:**
1. **Live API:** `https://polybackend-dev-test.up.railway.app` — if the endpoint already exists on the dev-test instance, hit it directly with `curl` to inspect shape and proceed against the real API (no mocking needed)
2. **`poly-backend/docs/<spec-name>-api.md`** — if it exists, read for intent + edge cases + BC status
3. **Mock-first fallback** — if the endpoint is not on dev-test AND no API doc yet:
   1. Generate `<repo>/docs/<spec-name>-<platform>.md` with a contract sketch in §6 marked `TBD: poly-backend#<n> finalizes`
   2. Build the mock provider so it returns full snapshots for every state from spec §5
   3. Wire the `MOCK_<MODULE>` build flag (xcconfig on iOS, gradle.properties on Android) so the dev can run the screen against mocks without a backend
   4. When the backend issue merges + ships to dev-test → swap to real API, flip the mock flag to false, re-test

Do NOT ask "impl-doc или spec?" — `impl-doc` is correct. The API gap is handled by the live URL + mock layer, not by switching mode.

## Acceptance criteria

> **Note on checkboxes.** The issue body is treated as a **static contract** — it lists what must be true at completion, not a working checklist. Reviewers tick the same items off in the **PR description's "Test plan" section**, which is the working checklist. When the PR merges with `Closes #<issue-number>`, the issue auto-closes regardless of body checkboxes. This avoids busy-work syncing two checklists.
>
> Mark a criterion `[x]` here only if the work was already done before the issue was created (e.g. impl-doc generated by `/architect impl-doc` immediately prior). Otherwise leave `[ ]` — the PR's Test plan tracks completion.

- [ ] Impl-doc exists at `<repo>/docs/<spec-name>-<platform>.md` and matches IMPL_DOC_TEMPLATE
- [ ] **API doc** (if backend) exists at `poly-backend/docs/<spec-name>-api.md` with all endpoints documented (request, response, key fields, errors, edge cases, BC table)
- [ ] All flows from spec section 4 implemented
- [ ] All states from spec section 5 covered
- [ ] All business rules from spec section 7 enforced
- [ ] Tests per spec section 9: happy + 401/403/404 (backend) or state transitions (UI)
- [ ] No drift between code and API doc — `/architect review` passes
- [ ] **Backward compatibility verified** (backend only) — no removed/renamed/retyped fields on existing endpoints; legacy compat fields documented in `<spec-name>-api.md` BC table per `feedback_backward_compat_endpoints`
- [ ] **Verification evidence** (backend only) — Tier 1 + Tier 2 outputs (ruff / mypy / import smoke / alembic / pytest) included in PR body, not "skipped, reviewer please run", per `feedback_backend_verification_gate`
- [ ] PR opened against the integration branch from `.claude/CURRENT_INTEGRATION_BRANCH` (currently `<RESOLVED-BRANCH>`)
- [ ] PR description references this issue (`Closes #<issue-number>`) and mirrors these criteria in its Test plan
```

## Step 5 — Create issues (after approval)

Sequence:
1. **For epics** — create the epic issue first, save its number
2. Create each sub-task issue with the epic reference in body
3. Each issue:
   - `gh auth status` — verify `whywolfy` is active
   - `gh issue create --repo 321-fit/<repo> --title "..." --body "..." --label "phase-4,module:<x>,repo:<x>" --assignee <username>` (multi-assign for backend: repeat `--assignee`)
   - Capture issue URL from output
4. Add each created issue to Project #2:
   - `gh project item-add 2 --owner 321-fit --url <issue-url>`
5. **For epics** — `gh issue edit <epic-number> --body "..."` to insert real sub-task links into the tracking checklist

After all issues are created, print a summary:

```
Created N issues for spec <spec-name>:
  - 321-fit/poly-backend#<n>  feat(<module>): <module> backend
  - 321-fit/321fit_ios#<n>    feat(<module>): <module> iOS
  - ...
All added to Project #2.
```

## Safety nets

- **NEVER** create issues without explicit user approval at Step 4
- **NEVER** rename existing backend endpoints in issue bodies — extend in place per `feedback_keep_existing_endpoints`
- **NEVER** propose components that don't exist in design-tokens — verify against `design-tokens/docs/components.md` and `Sources/FitUI/Components/` listing
- If a referenced screen ID does not exist in the prototype, flag it instead of inventing — ask the user
- All issue bodies in **English** per `feedback_skills_language`
